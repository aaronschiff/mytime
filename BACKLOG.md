# Backlog

## Deferred features for future work

- **Auth & HTTPS — resolved via Tailscale (2026-07-10):** Tailscale was adopted for this LAN (see README's "Remote access" note). `tailscale serve` now exposes mytime over a real, auto-renewing HTTPS cert on a tailnet-only address, resolving the "Not Secure" warning and enabling secure remote access. Security boundary is Tailscale tailnet membership (confirmed single-user tailnet — only the user's own devices), not application-level auth; app-level auth was deliberately not added given that trust boundary. LAN access (`http://bbbee.local:8000`) is unchanged and still available. Revisit app-level auth only if the tailnet is ever shared with other people. See `docs/superpowers/specs/2026-07-10-tailscale-remote-access-design.md`.

  - **Deferred: keep a running entry running through Full Edit.** Editing a running entry currently stops it first (existing backend behavior in `edit_entry`), then applies the edit. User asked (2026-07-05) whether editing should instead keep the entry running, continuing from the edited time. Requires changing `mytime/routers/api_today.py`'s (or the underlying service's) `edit_entry` behavior — out of scope for the menubar-only plan that shipped the frontend above.
  - **Check web app for the same edit-a-running-entry data-loss bug.** Final review of the menubar app (2026-07-05) found that editing a running entry without touching the duration field silently discarded its accumulated running time, because the edit form prefilled duration from stale stored `base_seconds` rather than live elapsed, and `edit_entry` overwrites the total unconditionally from the submitted duration. Fixed on the menubar client by prefilling from live elapsed instead. The web app's own Time-page edit form (`mytime/templates/*`) may have the same prefill issue against the same backend behavior — not checked yet.
  - **Revisit Esc-dismiss and Settings-window-reopening if a status-item-access library is ever adopted.** Both were tried and reverted during the 2026-07-06 polish pass: dismissing `MenuBarExtra`'s dropdown via any `NSApp`-level call (`.close()`, `NSApp.hide(nil)`) leaves the status-item icon stuck highlighted with no supported reset API, and there's no supported way to reopen the dropdown after a true-modal Settings dialog closes. A library like `MenuBarExtraAccess` (gives direct access to the underlying `NSStatusItem`) could fix both, but wasn't adopted this round — user preferred no added dependency. See `docs/superpowers/specs/2026-07-06-menubar-polish-1-design.md`.
